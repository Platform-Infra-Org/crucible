Terraform or Crossplane

Crucible builds every AWS lab with Terraform. Crossplane could do the same job from inside Kubernetes. This page explains how each one works here, what would change if labs moved to Crossplane, and what Crucible would gain and lose.

How each one works

Both are declarative: you describe what should exist (a bucket, a server) and the tool works out how to create it. They differ in when they act and where they remember what they made.

Terraform

  • A program you run. terraform apply compares your files with what exists, makes the difference, and exits.
  • Files in HCL, its own language: resource "aws_s3_bucket" "forge" { … }.
  • Remembers what it made in a state file (for labs: labs/<id>.tfstate in S3).
  • terraform destroy reads the state and deletes exactly what it made.
  • Between runs it does nothing. If someone changes a resource by hand, it stays changed until the next run.

Crossplane

  • A set of controllers that keep running inside Kubernetes. Each cloud has a provider (for AWS, split into families such as S3 and EC2).
  • Resources are Kubernetes objects in YAML: kind: Bucket, kind: Instance. Compositions bundle several into one template.
  • What it made lives in those objects, in the cluster's database. No state file.
  • Delete the object and the cloud resource goes too.
  • It reconciles continuously: when the cloud drifts from the YAML, it changes the cloud back.

One fact that often surprises people: the main AWS provider for Crossplane is generated from Terraform's own AWS provider. Under the hood the same AWS calls are made; what changes is the workflow around them.

One lab, two ways

Everything around the tool stays the same: the request, the approval, the one-hour credentials for the lab role, the crucible:lab-id tags that IAM insists on, the tag sweep and the hourly reaper. Only the middle changes.

When each one acts

This is the difference that matters most for labs. Many lab tasks ask the trainee to change the resources: resize an instance, fix a security group, add a bucket policy.

For labs, constant reconciling is usually the wrong behaviour.A break-fix task, or any task that asks the trainee to change the infrastructure, would be quietly reverted. Every lab resource would need management policies that leave out updates, and lint would have to enforce that.

The platform itself

The persistent and main stacks build the very server Kubernetes runs on. Crossplane lives inside Kubernetes, so it can't be what creates it.

Advantages and disadvantages

Terraform for labs

Advantages

  • Already built, tested and documented end to end.
  • infracost prices labs, so approvals and budgets work.
  • Acts only at start and end, so trainees' changes stand.
  • Nothing runs between labs; light on the single server.
  • Each lab's credentials stay inside its own pods.
  • The language most cloud material is written in.

Disadvantages

  • A state file per lab, readable with the lab's credentials.
  • A failed apply or destroy needs a retry run; nothing heals on its own.
  • Drift during the lab goes unnoticed until destroy.

Crossplane for labs

Advantages

  • Native to Kubernetes, where labs already live: objects, status and events in one place.
  • No state file, so nothing sensitive in S3 for trainees to read.
  • Keeps retrying on its own after a transient AWS error.
  • Compositions can give authors simple building blocks ("a small box with its own security group").
  • Good for labs that teach Crossplane or platform engineering.

Disadvantages

  • No infracost: every lab would need our own price estimate before approval.
  • Reverts trainees' changes unless every resource limits its management policies.
  • Always-on controllers and custom resource definitions on a small server.
  • One provider pod holds every running lab's credentials.
  • No default tags; Crucible must inject them.
  • Lint, preview, docs and authors all start from scratch.

If we adopted Crossplane

As a second engine for AWS labs, beside Terraform, never as a replacement. A lab would choose it with something like engine: crossplane under runtime: aws.

  1. Try it small, in dry run

    On the kind cluster from make cluster-check: install Crossplane and only the S3 provider, and build one bucket for one lab with that lab's credentials. Measure the memory the controllers use.

  2. Solve pricing

    An estimator that turns a lab's objects into an hourly price (instance types and volume sizes against the AWS Price List), so approvals and budgets keep failing closed.

  3. Solve reverting

    Require management policies of create, observe and delete on every lab object, and make lint refuse anything else.

  4. Wire the runner

    A per-lab ProviderConfig pointing at the lab's credentials Secret (renewed hourly, as today); tags stamped into every object; readiness from Ready conditions; deletion and waiting at the end; the same sweep and reaper.

  5. Tighten the cluster

    Extend the service account's permissions and the admission policy only as far as Crossplane objects in lab namespaces.

  6. Authors and docs

    Lint rules, preview support, a building-block page, the test guide and the AWS guide.

Check before deciding.Crossplane has changed a lot between versions. Older releases make managed resources cluster-wide; newer ones (v2) can keep them inside a namespace, which suits one namespace per lab far better. Confirm the current behaviour of namespacing, management policies and the AWS provider's tagging before planning the work.
