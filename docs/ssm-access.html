Crucible · reaching the app

Reaching the app over SSM

The app runs on a k3s node inside a VPC that accepts nothing from the internet, so there is no URL to hand anybody. This page explains why, and how a colleague with our AWS access opens a tunnel to it in three commands — what AWS Systems Manager Session Manager is for. It is a stopgap for a handful of people, not the app's access story.

The problem

Why there is no URL

Every spoke subnet in this VPC routes outbound through a Gateway Load Balancer endpoint, then a Network Firewall, then a dedicated NAT subnet, then an internet gateway named egress-igw. That is the design, and it is one-way: no subnet here has an inbound path from the internet — not for this instance, not for a load balancer, not for anything you could place in the existing subnets. A public IP on the instance was tried and was unreachable, for exactly this reason.

Other ways in are closed too. The VPC has no Transit Gateway attachment, so there is no route to an office or company VPN. The organization’s policies (SCPs) deny Elastic IPs, load balancers (internal and internet-facing), Client VPN and our own VPC endpoints and routes. The SSM Agent’s own traffic has no VPC endpoint either: it leaves through the central firewall and NAT to the public SSM endpoints (ssm, ssmmessages and ec2messages in il-central-1), so the firewall must allow them. If it does not, crucible aws up and crucible aws status stop with node not reachable over SSM and name the three hosts to ask the network team for.

So the question is not “which port do we open”. Nothing can be opened from this side. What is left is a path that needs only outbound connections at both ends, which is what Session Manager gives us.

The mechanism

How the tunnel works

Neither side ever accepts an inbound connection. Both dial out to the same AWS service, which bridges the two calls once it has checked who each one is.

  1. The instance dials out at boot

    Its SSM Agent registered itself the moment it booted, using the IAM role attached to the instance, and holds that outbound connection open.

  2. You dial out on your laptop

    crucible aws connect runs aws ssm start-session, which opens your own outbound connection to the same service, carrying your SSO identity.

  3. AWS bridges the two

    Both connections already exist, both were opened outbound, and neither side accepted anything inbound. That is why this works where a load balancer cannot.

  4. The plugin opens a local port

    For port forwarding, session-manager-plugin — a separate binary from the AWS CLI — opens a plain port on your laptop and shuttles bytes between it and the tunnel.

Why this is not a hole in the firewall

Both ends prove who they are before AWS joins them: the instance by its IAM role, you by your SSO login. Someone without valid, permitted credentials is never bridged — there is nothing exposed for them to knock on.

Scope

Who can use it

Colleagues who already hold the same AWS SSO access we do — the Workload-Admin-PS role in our Identity Center. Josh, for instance. Anyone without that role cannot use this path at all, and no amount of scripting changes that.

Not an "internal users" solution

If people without AWS access need to reach the app, this plan does not stretch to cover them. That is a different and bigger problem — a real ingress path from the networking team, or a VPN — and it is out of scope here.

Once per person

One-time setup

  1. Install the AWS CLI v2

    Version 2 specifically; the v1 packages in most distributions will not do.

  2. Install session-manager-plugin

    It is not bundled with the CLI and has its own installer per operating system. This is the step people miss. crucible aws connect checks for it and says so if it is missing.

  3. Point the CLI at our Identity Center

    aws configure sso, then pick the Workload-Admin-PS role.

  4. Get the crucible command

    From a clone of the repository: go install ./cmd/crucible. It needs no Terraform state; it finds the node by its tag.

Every session

Connecting

Sign in, then run one command. It stays open while you use the app.

aws sso login --profile workload-admin-ps
export AWS_PROFILE=workload-admin-ps
crucible aws connect --region il-central-1

It finds the running instance named crucible, reads the port from the node's crucible:public-url tag, and prints Crucible is at http://localhost:18080 while this runs; Ctrl-C closes it. Then it opens the tunnel. Open that address in a browser. Ctrl-C ends the tunnel; it exits quietly.

  • --region falls back to your AWS CLI region. --name picks another node name, if two are running.
  • --port is refused unless it is the port in Crucible's address. A different port breaks sign-in and saving, so leave it out.
  • It refuses with a message if the node has no crucible:public-url tag (run crucible aws up), if the install has a public URL (open that instead), or if the plugin is missing.

Caveats — real, not hypothetical

WhatWhy it bites
The tunnel reaches the host, not a pod It lands on a port on the EC2 instance itself. The app's Service has to be bound on the instance's host network on port 80. k3s's Traefik/ServiceLB does this for a LoadBalancer Service. Otherwise the tunnel connects to nothing.
It expires, twice over The SSO login lasts hours (org policy decides), and the SSM session itself times out after about 20 minutes idle. Re-running crucible aws connect is routine, not a one-off.
One tunnel per person Each person runs their own session on their own laptop, all on the same local port (default 18080): Crucible's public URL is http://localhost:18080, so a different port breaks sign-in and saving. Laptops don't collide, but there is nothing to route people to collectively; it is not a reverse proxy.
ssm:StartSession is assumed, not verified Likely covered by how broad Workload-Admin-PS is, but confirm it on this instance once, rather than finding out mid-demo.
The firewall must let the node out The node reaches SSM, S3, Docker and GitHub through the central firewall. crucible aws status tests each host from the node and lists the ones it blocks under egress:; send that list to the network team. The list includes the apt mirrors (plain HTTP), Cognito's login domain and the AWS-lab hosts (Terraform registry, IAM, EC2, tagging, CloudTrail). It first prints ssm:; if that is not Online, it skips the other checks and names the three SSM hosts. If they are blocked at up, you see node not reachable over SSM instead. Your git host is not tested; check it by hand.
How Crucible works through the tunnel
  • Everyone uses the same local port (init --local-port, default 18080). Crucible’s public URL must equal the address in the browser, or the Origin check refuses every change.
  • CRUCIBLE_PUBLIC_URL and the Cognito callback are http://localhost:18080 (Cognito accepts plain http only for localhost).
  • Traefik serves plain HTTP on port 80 with --access ssm.
  • Laptop agents reach Crucible through the same tunnel, so laptop and cluster labs work only while it is open.
  • Webhooks do not arrive, so Crucible polls every 60 seconds.

The real fix

When it outgrows this

The actual answer is a genuine ingress path: a load balancer in a subnet that is reachable from outside, which does not exist anywhere in this VPC today and would have to be provisioned by the networking team. Worth raising with them the moment this stopgap starts being used as more than a stopgap.

A second option is a Cloudflare Tunnel. A small cloudflared process on the node dials out to Cloudflare, so it needs no inbound path, no Elastic IP and no load balancer, and Cloudflare Access can gate the hostname by the company identity provider. It needs the firewall to allow Cloudflare, the domain on Cloudflare and the security team’s approval. The design is in deploy-architecture.html.
