Crucible · how it is deployed

Crucible Deploy Architecture

Crucible is one Go process that serves the API and the React app, backed by Postgres and an OIDC sign-in. The same process runs in three settings: on your laptop under Docker Compose, in the kind-based end-to-end check, and in production on a single k3s node in AWS, with AWS labs in a lab account. This page draws each one from the files in deploy/, then follows production down to who holds which AWS permission, how an AWS lab runs, and how a release ships.

The production drawings show what deploy/aws builds today: an Elastic IP, a public domain with a Let's Encrypt certificate, and ideally a separate lab account. Our account allows none of that, so it runs differently: one account, no inbound path, and for now everyone reaches the app through an SSM tunnel. Our account and Reaching Crucible explain it, and each affected section has an In our account note. Nothing of Crucible is deployed there yet.

New to AWS? The AWS and networking primer explains the words used here. To build it, follow the deployment walkthrough, every command in order.

Local stack

Three containers and no Kubernetes. Open http://localhost:8080; you sign in on Keycloak, and the app talks to Postgres. Labs run outside Compose, through the laptop agent.

Start and stop it

crucible local up runs make build, make toolbox and ./scripts/seed-git.sh, then docker compose … up -d --build --wait. Add --keycloak-port 8082 when 8081 is taken. crucible local down stops it and keeps the data; --wipe deletes it.

Configuration

Settings, teams and budgets live in Postgres. CRUCIBLE_SEED_DIR imports examples/platform once, into an empty database only; its trainings' repositories arrive connected. CRUCIBLE_GIT_ALLOW_FILE=1 lets file:// repositories through, and a development CRUCIBLE_SECRET_KEY lets you try tokens and deploy keys under Administrator → Repositories.

Labs

The agent on your laptop runs laptop labs in Docker, and cluster labs on whatever cluster your kubeconfig points at. AWS labs are off here.

scripts/cluster-check.sh · deploy/compose/cluster.yml

cluster-check: the end-to-end proof

The same Compose stack, plus a kind cluster named crucible-m4 after milestone 4 (the cluster runtime). The API joins kind's Docker network and acts as the crucible service account, so the production RBAC and admission policy apply to it. It never touches ~/.kube/config or your platform cluster.

What it proves

Lab isolation on a real cluster: quota, the default-deny NetworkPolicy, the IMDS block, and that the service account can't write outside lab namespaces. Then the full browser journeys, including an AWS lab from estimate to Ledger and a cluster lab through the agent.

Why it takes ~35 minutes

Most of the time is building and booting: Go binaries, the web build and tests, the API and toolbox images, the kind cluster, the stack, then 12 journeys in sequence (about 8 minutes).

Faster loop

With KEEP=1 the stack stays up. Rebuild only the API and re-run one spec. Journeys that expect a fresh trainee need a fresh stack.

deploy/aws/persistent · deploy/aws/main · deploy/aws/labs

Production on AWS

Three Terraform stacks. persistent holds what must survive a rebuild: sign-in, the data bucket, Terraform state and the key that seals repository credentials. main is the node and everything around it; it can be torn down and rebuilt from the latest snapshot. labs lives in the lab account, where trainees' AWS labs create real resources inside hard limits. The drawing is the code's design: a separate, standalone lab account and a public address.

The node needs no keys of its own: it acts as an IAM role, and that role may only read its bucket and parameters, write its backups and uploads, and assume the three lab-account roles (IAM roles). To build all three stacks, follow crucible aws up in the deployment walkthrough.

In our account.One account holds all three stacks, so the lab-account column is the same account as the main one. There is no Elastic IP, no public URL, no DNS record and no Let's Encrypt: the VPC has no inbound path, and the organization's SCPs deny Elastic IPs and load balancers. People and laptop agents reach the node through an SSM tunnel instead (today), and the git host's webhook can't arrive, so Crucible fetches every 60 seconds. Outbound calls, to the git host, the Price List and AWS's own APIs, leave through the networking team's firewall and NAT. deploy/aws/main can't deploy here until the changes listed under the main stack are made; they are not made yet. Our account

These facts shape how Crucible runs for us. They were checked with read-only describes, EC2 --dry-run calls and requests built to fail validation; nothing was created.

One account

  • 133089468093 (Gray-Hippo-SandboxCloudEngineering-PRD-001), region il-central-1, under an AWS Organizations landing zone (Control Tower).
  • We sign in through Identity Center as Workload-Admin-PS.
  • No separate lab account: AWS labs run in this same account.
  • Nothing of Crucible exists here yet: no instances, load balancers, Crucible buckets, parameters or roles.
  • The organization runs after-hours automation (roles such as afterhours-shut-down-role and EC2Stop-Role) that probably stops instances out of hours. What it targets isn't confirmed; check with the platform team.

One VPC, built by the networking team

  • vpc-03aa39198d92c5a25, 10.2.128.0/22, from the stack SPOKE-Networking-133089468093-Stack. There is no default VPC: the organization deletes it.
  • Workloads go in spokeSubnet1 (10.2.129.0/24, AZ 1a) or spokeSubnet2 (10.2.130.0/24, AZ 1b). No public IPs on launch; about 251 free addresses each.
  • No Transit Gateway attachment, so no route to an office or the company VPN.
  • No VPC endpoints except the firewall's, so the node's SSM, S3 and STS calls go out to the public AWS endpoints. The firewall must allow them; which hosts it allows isn't verified.

The way out, and no way in

  • Spoke subnet, then a Gateway Load Balancer endpoint into the central inspection firewall (RootHub-inspection-firewall, run from the hub), then a firewall subnet, a NAT gateway, and the internet gateway …-egress-igw.
  • Both spoke subnets use the route table spoke-rt-1b, so both currently leave through the 1b firewall endpoint.
  • The internet gateway only sends return traffic back through the firewall. A public IP on an instance is allowed but unreachable: a colleague tried it.
  • The account's two Elastic IPs (001-eip-1a, 001-eip-1b) belong to the NAT gateways, not to us.

How people reach Crucible

Reaching Crucible

The code's design gives the node a public domain. Our VPC has no inbound path, so that can't work here. Today the way in is an SSM tunnel; a Cloudflare Tunnel is the option for later.

Today: an SSM port-forward

Each person with our Identity Center access runs a Session Manager port-forward from their laptop to port 80 on the node, then opens http://localhost:18080. The laptop and the node's SSM agent both dial out to AWS Systems Manager, which joins the two, so nothing has to accept an inbound connection. Setup, the connect script and its caveats: reaching the app over SSM.

The same local port for everyone

Crucible's public URL must equal the address in the browser: the Origin check refuses state changes from any other origin, and the Cognito callback URL is built from it. So everyone's tunnel listens on 18080, with CRUCIBLE_PUBLIC_URL=http://localhost:18080 and the Cognito callback http://localhost:18080/auth/callback. Cognito accepts plain http only for localhost.

Traefik serves plain HTTP

Today Traefik redirects port 80 to HTTPS and requests a Let's Encrypt certificate. Let's Encrypt's HTTP-01 check can't reach the node, and the redirect breaks the tunnel, so Traefik must serve plain HTTP on port 80. Not changed yet (the list).

Agents and webhooks

A laptop agent reaches Crucible through its own laptop's tunnel, so laptop and cluster labs work only while that tunnel is open. GitHub webhooks can't arrive at all, so Crucible fetches every repository every 60 seconds instead.

Who can use it

Only people with our AWS access. The SSO login lasts hours and an idle session ends after about 20 minutes, so re-running the connect script is routine.

Later: a Cloudflare Tunnel into the VPC

A design only; none of it is built. cloudflared runs on the node and dials out to Cloudflare, so it fits the SCPs: no Elastic IP, no load balancer, no internet gateway of our own. A company hostname points at Cloudflare, Cloudflare Access asks for the company sign-in, and allowed requests come back down the connection cloudflared already opened. Anyone with a company account could then use Crucible, agents would work from anywhere, and webhooks could arrive.

Crucible's own programs Not built yet Cloudflare, or our account Connection opened in this direction

How it would be set up

  • Create the tunnel in the Cloudflare Zero Trust dashboard to get a tunnel token, and add a public hostname, crucible.<company domain> → http://traefik.kube-system.svc:80. Cloudflare creates the DNS record.
  • cloudflared runs as a small Deployment in the Helm chart, two replicas, with the token in the crucible-secrets Secret, sourced from an SSM SecureString like the other secrets.
  • An Access policy lets in company emails or a group; two bypass rules leave /api/agent/ws and /api/git/hook to Crucible's own checks.
  • TLS ends at Cloudflare, so Traefik stays HTTP-only, exactly as for the SSM tunnel.
  • The public URL and the Cognito callback move to the Cloudflare hostname. The Origin check keeps working, since browsers send that hostname.

What it needs

  • The firewall to allow *.argotunnel.com and *.cloudflare.com on 7844 (TCP and UDP), or 443.
  • The company domain, or a subdomain of it, on Cloudflare.
  • The security team's approval: Cloudflare decrypts traffic at its edge, the tunnel is a path into a VPC built to have no ingress, and the two bypassed paths are reachable from the internet, guarded only by Crucible's checks.
  • Cloudflare Zero Trust is free up to 50 users; check the current plans.

What isn't built

  • The cloudflared Deployment and its token in the chart and in deploy/aws/main.
  • Optional: an Access service token for the agent, so /api/agent/ws needn't bypass Access. That is an agent change.
  • Optional: trusting Access's own token for sign-in, so people sign in once instead of twice. That is a code change. Both sign-ins can use the same identity provider, so the second is usually one click.
  • The main-stack changes the SSM path needs too.

deploy/helm/crucible · rbac.yaml

Inside the node

k3s runs everything on the one node. The Helm chart installs Crucible, Postgres and the backup job in namespace crucible. Each AWS lab gets its own lab-<id> namespace, and estimates run in crucible-estimates. Two guards limit what the API's service account can do, even if the API itself were compromised.

Why one replica

The agent links, locks and live terminals are held in memory, so the chart pins replicas: 1 and a Recreate rollout. Scaling out would need a shared hub.

AWS credentials

Pods that call AWS take the node role's credentials from the metadata service. Lab pods are cut off from it, because that role can assume any lab's role. Who acts as which role, and why: IAM roles.

In our account.Traefik can't get a Let's Encrypt certificate here, and its redirect to HTTPS breaks the SSM tunnel, so it must serve plain HTTP on port 80, where the tunnel lands. That change isn't made yet (the list). Everything else inside the node is the same.

deploy/helm/crucible · backup.yaml

Backups

Postgres holds everything that isn't in git: configuration, people, progress and spend. It is dumped to the data bucket every evening, and a rebuilt node restores it before Crucible starts.

When

The CronJob crucible-backup runs at 19:15 every day (Europe/Bucharest), before the node sleeps at 19:30. crucible aws snapshot runs it on demand, and up, sleep and teardown take a snapshot first unless you pass --no-snapshot.

What is kept

Dated dumps under snapshots/ expire after 30 days. latest/crucible-latest.dump is kept for good, so a long teardown can still be restored.

Restore

On an empty database the API's init container fetches the newest snapshots/ dump, falling back to latest/, and runs pg_restore. A teardown and up therefore comes back with its data.

IAM roles: who acts as whom

An IAM role is an identity with no password and no permanent keys. Its trust policy says who may become it (sts:AssumeRole). Its permission policies say what the temporary credentials it hands out may do, and those credentials expire within hours. A permission boundary and the organization's SCPs can only narrow that, never widen it. The primer explains roles in general; this section is how Crucible uses them.

How the node gets a role: IMDS

An instance profile puts the role crucible-node on the EC2 node. Programs there ask the instance metadata service (IMDS) at 169.254.169.254 for fresh credentials, so no keys sit on disk. The node requires IMDSv2 (http_tokens = "required": every request needs a token) with http_put_response_hop_limit = 2, so pods, one network hop past the host, can reach it too.

Why lab pods can't reach it

The node role may assume any lab's role. So lab pods are blocked from IMDS three ways: a NetworkPolicy egress deny to 169.254.169.254, AWS_EC2_METADATA_DISABLED in the pod, and an init container that waits until the block is in place. A trainee in a workspace only ever holds their own lab's credentials.

Walkthrough: the nightly Postgres snapshot

  1. The CronJob starts a pod ns crucible

    At 19:15 Europe/Bucharest the CronJob crucible-backup starts a pod from postgres:18-alpine.

  2. It dumps the database backup pod

    pg_dump -Fc writes /tmp/db.dump, with the password from the crucible-secrets Secret.

  3. It gets credentials IMDS · node role

    aws s3 cp finds no keys, so it asks IMDS with an IMDSv2 token. IMDS returns the node role's temporary credentials.

  4. S3 checks the node role's policy data bucket

    PutObject on snapshots/crucible-<UTC>.dump and latest/crucible-latest.dump is allowed. PutObject on releases/* would be denied, so a backup pod can't replace a release.

  5. On demand operator SSM agent · node role

    crucible aws snapshot runs with the operator's role and calls ssm send-command. The SSM agent, as the node role, runs /opt/crucible/snapshot.sh, which creates a Job from the CronJob and waits up to 15 minutes. up, sleep and teardown do this first unless --no-snapshot.

  6. Restore API init container node role

    On an empty database, the API pod's init container uses the same node-role credentials, with ListBucket and GetObject, to fetch the newest snapshots/ dump (falling back to latest/), and pg_restores it.

Walkthrough: an AWS lab starts

  1. The API assumes the lab role API pod node role

    With node-role credentials from IMDS, the API calls sts:AssumeRole on crucible-lab with the session tag crucible:lab-id=<id>.

  2. STS returns lab credentials lab role

    They last one hour. Crucible stores them as a Secret in the lab's lab-<id> namespace and refreshes them about every 45 minutes while the lab runs.

  3. Terraform builds the lab tf-apply pod lab role

    The apply pod uses those credentials. Every call is checked against the lab role's policy and the boundary (the IAM fence).

  4. The node role stays out of reach lab-<id>

    Lab pods are blocked from IMDS, so they never see the node role.

Estimates use the plan role the same way, read-only and without session tags; the reaper and the Ledger use the ops role.

The IAM fence

Three IAM pieces keep labs apart: the trust policy decides who can become the lab role, the permission boundary caps what the role can ever do, and the role's own policy limits each session to its own lab. A lab may do only what both the boundary and the role policy allow.

The permission boundary

  • Ceiling: ec2:*, s3:*, reading one's own identity and tags. Nothing else, ever: no IAM, no other services.
  • OnlyLabRegions: every call outside the allowed regions.
  • SmallInstancesOnly: anything but t3.nano/micro, t3a.nano/micro, t4g.nano/micro (configurable).
  • SharedTenancyOnly, NoMarketplaceImages.
  • SmallVolumesOnly, GeneralPurposeVolumesOnly, BaselineIops/ThroughputOnly: volumes up to 50 GiB of gp2/gp3.
  • NoBucketLocks: no object lock, bucket policies or ACLs that could stop the cleanup.

The lab role's policy (attribute-based access)

  • CreateTagged: launch instances, create volumes and security groups only if the request carries crucible:lab-id equal to the session's.
  • ManageOwn: change and delete only resources carrying the session's lab id.
  • OwnSecurityGroupsOnly, NotOtherLabsNetwork: no launching into the shared default group or another lab's group.
  • KeepCrucibleTags, NoBlankDeleteTags: lab tags can't be changed or stripped.
  • OwnBuckets, OwnState: S3 buckets named crucible-lab-<id>… and only its own state file.
  • Read: Describe* calls, needed by Terraform (these are account-wide).

Why tags, and not an account per lab?One shared lab account is quick and cheap to run. Tags plus IAM conditions give each lab its own fence inside it. The trade-off is that isolation is best effort: a trainee can see other labs' resources through Describe calls, though not change them. That is why a dedicated sandbox account is recommended.

In our account: labs share Crucible's own account.There is no second account, so the fence is all that keeps labs apart from Crucible itself. A lab session can't change the node, its role or its buckets, because they carry no lab tag, but its Describe calls can see them, along with the networking team's VPC.

An AWS lab, start to finish

An AWS lab is a folder in a training repo: a lab.yaml, task instructions, check scripts, and a Terraform module that builds what the trainee will work on. Crucible runs that module for each trainee, in the lab account, with credentials that can only touch that one lab. Prices come from the free public AWS Price List, and spend from the lab's own Terraform state, then from the free billing export. If price data is missing or stale, the lab can't be requested; Crucible never quotes $0.

In our account.Labs run in this same account, in il-central-1, where our only VPC is. With no default VPC, a lab module that launches an instance has to place it in a spoke subnet; it gets no public IP and reaches the internet through the firewall. Elastic IPs, NAT gateways and load balancers in a lab module are denied by the SCPs as well as by the lab role. A lab like Cloud Heat below, S3 only, needs no network.

lab.yaml (Forge 401, "Cloud Heat")

id: cloud-heat
runtime: terraform
cloud: aws
ttl: 1h
idle_timeout: 30m
terminals:
  - { name: workspace, service: workspace }
tasks:
  - id: t2-bucket
    instructions: tasks/02-bucket.md
    check: { script: checks/02-bucket.sh, run_in: workspace }
    points: 2
aws:
  region: eu-west-1
  max_hourly_usd: 0.05
  usage:
    aws_s3_bucket.forge: { storage_gb: 1 }

terraform/main.tf

# Crucible adds the provider (region,
# crucible:* default tags) and the state
# backend. The module never declares them.
resource "aws_s3_bucket" "forge" {
  bucket        = "crucible-lab-${var.crucible_lab_id}"
  force_destroy = true
}

Next to the module Crucible writes crucible.tf: an S3 backend for labs/<id>.tfstate, the AWS provider with the lab's region, and default tags crucible:lab-id, crucible:team and crucible:training on everything the module creates. The lab id is passed in as var.crucible_lab_id.

  1. Estimate crucible-estimates plan role

    Once per content version, a one-off pod runs terraform plan on the lab's module, with a read-only plan-role session (15 minutes) and no state. Crucible prices each planned resource from the price list it refreshes weekly, plus the author's declared prices and the usage the lab states. The estimate is that hourly price × the lab's time limit. The plan is cached per content version, and prices are applied fresh on every view; the lab page shows the breakdown, resource by resource. Crucible refuses a lab above its own max_hourly_usd, in a region you haven't allowed, with a resource it can't price, or when its price data is missing or over 30 days old.

  2. Request and approval crucible

    The request shows the estimate, and the estimate picks an approval tier. AWS labs are never approved automatically: by price, the training's admins, the leaders of the team that owns it, or a Crucible admin approve. Team budgets and caps are checked before anyone can approve, and a request that would pass a budget cap needs an admin.

  3. Credentials lab-<id> lab role

    Crucible creates the lab namespace and a lab-role session tagged with the lab id: one hour, refreshed about every 45 minutes (walkthrough).

  4. Apply tf-apply lab role

    A tf-apply pod unpacks the module, runs terraform init (state labs/<id>.tfstate in the lab state bucket) and terraform apply. Every resource gets the lab's tags; IAM rejects any that would not. Crucible then reads the state with the ops role and starts metering: each resource at its list price, for as long as it exists.

  5. Work workspace pod

    A workspace pod with Docker-in-Docker, the AWS CLI, Terraform and kubectl backs the browser terminals, with the lab's credentials. Check and setup scripts run there too, server-side. The pods are blocked from the node's metadata service. Crucible re-reads the state every 15 minutes, so resources added from the terminal are metered too.

  6. End tf-destroy lab role

    The trainee ends the lab, or it reaches its time limit, idles, hits the schedule's close or a budget cap, or an admin stops all labs with the kill switch. A tf-destroy pod runs terraform destroy. The meter stops when the destroy succeeds.

  7. Sweep lab role

    Anything else carrying the lab's tag, say a volume the trainee made by hand, is found with the Tagging API and deleted with the lab's credentials, including instances with termination protection and untagged buckets named crucible-lab-<id>….

  8. Reaper ops role lab role

    Every hour the reaper lists tagged resources with the read-only ops role and deletes leftovers of labs that ended over an hour ago, each with a lab-role session for that lab. It reports to admins, and never deletes, anything tagged with a lab it doesn't know, or created untagged (seen in CloudTrail). If a destroy failed or couldn't run, the lab's meter stays open until a full run finds nothing of it left.

  9. Billed billing export ops role

    AWS writes the CUR 2.0 export daily. Every six hours Crucible reads it with the ops role and adds it up per crucible:lab-id, counted before credits. The Ledger shows the estimate, then the metered cost while the lab runs, then the billed cost, which replaces the metered one 48 hours after the lab ends. Independently, the AWS Budget emails admins at 80% and 100% of the month, whatever Crucible does.

Shipping a release

There is no container registry. Releases travel through S3: a release is a tarball in the data bucket that the node imports into containerd.

  1. Build your machine

    crucible aws deploy builds a Linux image of the current git commit with docker buildx (linux/amd64), saves and compresses it, and packages the Helm chart.

  2. Upload data bucket

    Both go under releases/<commit>/, then current-release is pointed at them.

  3. Roll out SSM node

    aws ssm send-command runs /opt/crucible/deploy.sh on the node, as the node role: it reads current-release, imports the image into containerd, runs helm upgrade --install with values and secrets from SSM, then checks /healthz.

On first boot the node's start-up script installs sysbox, k3s, Helm and the AWS CLI, sets Traefik up for Let's Encrypt, reads its settings from Parameter Store and runs the same deploy script; on an empty database the API restores the newest snapshot first. AWS labs in practice

Limits and good habits

Keep in mind

  • Trainees can read their own lab's Terraform state. Never put passwords, keys or tokens in lab state or outputs.
  • A credential leaked from a workspace stays valid up to an hour after the lab ends; leftovers it makes are reaped within about two hours.
  • An instance launched with a detached network interface (DeleteOnTermination=false) can leave an untagged interface behind. Check now and then: aws ec2 describe-network-interfaces --filters Name=status,Values=available.
  • The sweep and the reaper only look in allowed regions. End every lab in a region before removing it.

Good habits

  • Use a separate sandbox account for labs, with a budget alert of its own in AWS Budgets. We have one account, so our labs share it with Crucible; give labs-init a --budget-email.
  • Run one Crucible per lab account: the reaper reports, but never deletes, labs it doesn't know.
  • Keep backups of the three local state files: persistent, labs, and your crucible.tfvars.
  • Try a new lab in dry-run mode on your machine first (make cluster-check), where a fake account stands in for AWS.

Real AWS is tested by hand.Nothing in the automated suites touches real AWS. docs/runbooks/aws.md lists every check, and the test guide has the same steps as a checklist.
