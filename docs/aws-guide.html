The whole picture

Crucible is one program (the API) that serves the website, talks to its database and runs labs. On AWS it lives on a single virtual server. Everything else in the diagram exists to let people sign in, to keep data safe, to ship new versions, and to run AWS labs in a separate, fenced-off account.

AWS in ten minutes

The words this page uses, in plain terms, and where Crucible uses each one.

Account

Your own private area of AWS, with its own bill and its own users. Nothing in one account can touch another unless you allow it.

Crucible: one account for Crucible, ideally a second, throwaway "sandbox" account for labs.

Region

A group of data centres in one place, such as eu-west-1 (Ireland). Most things you create live in one region.

Crucible: everything in the region you choose; labs only in the regions you allow.

IAM

Identity and Access Management: who may do what. Permissions are written as JSON policies of Allow and Deny rules. A Deny always wins.

Crucible: the heart of lab safety. See the IAM fence.

Role

An identity with permissions but no password. Someone or something allowed by the role's trust policy can "assume" it and get temporary credentials.

Crucible: the server is the role crucible-node; labs act as crucible-lab.

STS and AssumeRole

The Security Token Service hands out short-lived credentials (here, one hour) when someone assumes a role. They expire on their own.

Crucible: assumes the lab role once per lab, and again every hour while it runs.

Permission boundary

A ceiling on a role: even if the role's own policy allows something, the boundary can forbid it. What the role can really do is the overlap of the two.

Crucible: the lab role's ceiling: EC2 and S3 only, small sizes, chosen regions.

Tags

Labels (key = value) you attach to resources. IAM can require them and check them: "you may delete only what carries your tag".

Crucible: every lab resource carries crucible:lab-id; that tag decides who may touch it and what gets cleaned up.

EC2, AMI, EBS

EC2 is a virtual server. It starts from an AMI (a disk image) and keeps its files on EBS (a network disk).

Crucible: one EC2 server from the Ubuntu 24.04 AMI with an encrypted 60 GiB EBS disk; labs may start tiny EC2s.

VPC, subnet, security group

A VPC is your private network; a subnet is a slice of it; a security group is a firewall on a server.

Crucible: the default VPC's public subnet, and a security group that lets in only web traffic.

Elastic IP

A fixed public IP address you keep even when the server stops.

Crucible: your domain points at it.

Instance profile and IMDS

How a server gets a role: AWS gives it short-lived credentials through the instance metadata service at 169.254.169.254. IMDSv2 requires a token for that.

Crucible: the server uses it; lab pods are blocked from it, so they can never borrow the server's role.

S3

Simple Storage Service: files ("objects") in "buckets". Cheap, durable, private by default.

Crucible: releases, nightly database snapshots, uploads, and Terraform state.

Systems Manager (SSM)

Parameter Store keeps settings and secrets (encrypted); Session Manager gives you a shell on a server without opening SSH; Run Command runs scripts remotely.

Crucible: holds its settings and secrets; crucible aws deploy rolls out through it.

Cognito

A managed sign-in service: user accounts, passwords, email verification, a hosted login page. Free up to 10,000 monthly users.

Crucible: people sign in through it; Crucible trusts its verified emails.

EventBridge Scheduler

Runs AWS actions on a timetable, like a cron job in the cloud.

Crucible: starts the server in the morning and stops it at night on weekdays.

Route 53

AWS's DNS service: turns a name into an IP address.

Crucible: optional; you can point your domain at the Elastic IP with any DNS provider.

Cost Explorer and cost-allocation tags

Cost Explorer shows what you spent. Once a tag is activated as a cost-allocation tag, spend can be grouped by it.

Crucible: reads each lab's real bill by its crucible:lab-id tag.

CloudTrail

The audit log of API calls: who created, changed or deleted what, and when. 90 days of history are free.

Crucible: checks no lab created anything without its tag.

Terraform and state

Terraform creates infrastructure from text files. It remembers what it made in a state file, so it can change or destroy exactly that later.

Crucible: builds its own infrastructure, and runs every AWS lab, with Terraform.

k3s, Helm, Traefik

k3s is a small Kubernetes that runs on one server; Helm installs apps into it; Traefik is the web front door that also fetches HTTPS certificates from Let's Encrypt.

Crucible: runs as a Helm release on k3s, behind Traefik.

Deploy it

Everything runs from the repo root on your computer. You need an AWS account, a domain name you control, and a terminal logged in to AWS (aws configure or SSO) with administrator rights in that account.

  1. Install the tools

    Terraform 1.10 or later, AWS CLI v2, Docker with buildx, Helm 3, Go 1.26. Either install the CLI with go install ./cmd/crucible and type crucible …, or prefix every command with go run ./cmd/crucible.

  2. Create the persistent stack

    Makes the state and data buckets and the Cognito sign-in. Nothing it creates is ever deleted by Crucible.

    crucible aws init --region eu-west-1 --domain crucible.example.com

  3. Back up its state

    This file is the only record of what init created. Copy it to a safe place, and again after every init.

    aws s3 cp deploy/aws/persistent/terraform.tfstate s3://<state_bucket>/persistent.tfstate

  4. Fill in your settings

    Copy the example and edit it. domain must match the one you gave init. Set bootstrap_admin to your email: that person becomes the first admin.

    cp deploy/aws/main/terraform.tfvars.example deploy/aws/main/crucible.tfvars

  5. Build the server

    up runs Terraform on the main stack, waits for the server to come up, then deploys the current release. Right after the apply it prints Point an A record <domain> → <ip>: create that DNS record while it waits (skip this if you gave a Route 53 zone).

    crucible aws up

  6. Wait for HTTPS

    The first visit can take about a minute while Let's Encrypt issues the certificate. If up ends with "isn't answering yet", DNS is still settling: wait and check.

    crucible aws status

  7. Invite yourself and sign in

    Invite your bootstrap_admin email in Cognito (see docs/runbooks/cognito.md), sign in, and set up Crucible under Administrator → Forge settings: cost tiers, cluster lab rate, schedules, more admins. Then create teams and register trainings.

  8. Give the bot access to your training repos

    Set git_credentials (read, and push for content edits) and git_bot_email in your settings, and point your git host's push webhook at https://<domain>/api/git/hook with the secret from Parameter Store.

What happens when the server boots

The server configures itself from a startup script ("user data") the first time it starts:

  1. Install

    Sysbox (so cluster labs can run Docker safely), k3s, Helm and the AWS CLI. Traefik is set up to get Let's Encrypt certificates and redirect HTTP to HTTPS.

  2. Read its settings

    From Parameter Store, using its role. No secret is baked into the image or the disk.

  3. Restore, if the database is empty

    On a rebuilt server, an init step loads the newest snapshot from the data bucket before Crucible starts.

  4. Deploy the current release

    /opt/crucible/deploy.sh downloads the release named in s3://…/current-release, imports the image into k3s and installs the Helm chart.

How a new version reaches the server

There is no container registry; releases travel through S3. crucible aws deploy:

  1. Builds on your computer

    A Linux image of the current git commit with Docker buildx, saved and compressed, plus the packaged Helm chart.

  2. Uploads to the data bucket

    Under releases/<commit>/, then updates current-release.

  3. Rolls out through Systems Manager

    Runs deploy.sh on the server, which imports the image and upgrades the Helm release, then checks /healthz.

How AWS labs work

An AWS lab is a folder in a training repo: a lab.yaml, task instructions, check scripts, and a Terraform module that builds what the trainee will work on. Crucible runs that module for each trainee, in the lab account, with credentials that can only touch that one lab.

lab.yaml (Forge 401, "Cloud Heat")

id: cloud-heat
runtime: aws
ttl: 1h
idle_timeout: 30m
terminals:
  - { name: workspace, service: workspace }
tasks:
  - id: t2-bucket
    instructions: tasks/02-bucket.md
    check: { script: checks/02-bucket.sh, run_in: workspace }
    points: 2
aws:
  region: eu-west-1
  max_hourly_usd: 0.05

terraform/main.tf

# Crucible adds the provider (region,
# crucible:* default tags) and the state
# backend. The module never declares them.
resource "aws_s3_bucket" "forge" {
  bucket        = "crucible-lab-${var.crucible_lab_id}"
  force_destroy = true
}

Next to the module Crucible writes crucible.tf: an S3 backend for labs/<id>.tfstate, the AWS provider with the lab's region, and default tags crucible:lab-id, crucible:team, crucible:training on everything the module creates. A lab id is passed in as var.crucible_lab_id.

One lab, from request to bill

  1. The trainee asks

    Crucible prices the module with infracost (an hourly price from the Terraform) × the lab's time limit, and refuses a lab above its own max_hourly_usd or in a region you haven't allowed.

  2. A person approves

    AWS labs are never approved automatically. The price decides who: program approver, team leader, or admin. A request that would pass a budget cap needs an admin.

  3. Crucible gets credentials for this lab

    The server's role calls STS AssumeRole on crucible-lab, with the session tag crucible:lab-id=<id>. AWS returns credentials valid for one hour. Crucible writes them into the lab's Kubernetes namespace and renews them every hour while the lab runs.

  4. Terraform builds the lab

    A tf-apply pod unpacks the module, runs terraform init (state in the lab state bucket) and terraform apply. Every resource gets the lab's tags; IAM rejects any that would not.

  5. The trainee works

    A workspace pod with the AWS CLI, Terraform and kubectl backs the browser terminals. Check scripts and setup scripts run there too, with the same lab credentials. The pods are blocked from the server's metadata service.

  6. It ends and is destroyed

    At the time limit, after idling, when the schedule closes, at a budget cap, on End lab, or with the kill switch: a pod runs terraform destroy.

  7. The sweep catches leftovers

    Anything else carrying the lab's tag (say, a volume the trainee made by hand) is found with the Tagging API and deleted with the lab's credentials, including instances with termination protection and untagged buckets named crucible-lab-<id>….

  8. The reaper checks every hour

    Using the read-only ops role, it deletes leftovers of labs that ended over an hour ago, and reports to admins anything tagged with a lab it doesn't know, or created untagged (seen in CloudTrail).

  9. The real bill arrives

    Every six hours Crucible reads Cost Explorer grouped by crucible:lab-id. The Ledger shows the estimate first, then the real cost once AWS settles it, usually after 24–48 hours.

The IAM fence, in detail

Three IAM pieces keep labs apart: a trust policy that decides who can become the lab role, a permission boundary that caps what the role can ever do, and the role's own policy that limits each session to its own lab. A lab may do only what both the boundary and the role policy allow.

The permission boundary

  • Ceiling: ec2:*, s3:*, reading one's own identity and tags. Nothing else, ever: no IAM, no other services.
  • OnlyLabRegions: every call outside the allowed regions.
  • SmallInstancesOnly: anything but t3.nano/micro, t3a.nano/micro, t4g.nano/micro (configurable).
  • SharedTenancyOnly, NoMarketplaceImages.
  • SmallVolumesOnly, GeneralPurposeVolumesOnly, BaselineIops/ThroughputOnly: volumes up to 50 GiB of gp2/gp3.
  • NoBucketLocks: no object lock, bucket policies or ACLs that could stop the cleanup.

The lab role's policy (attribute-based access)

  • CreateTagged: launch instances, create volumes and security groups only if the request carries crucible:lab-id equal to the session's.
  • ManageOwn: change and delete only resources carrying the session's lab id.
  • OwnSecurityGroupsOnly, NotOtherLabsNetwork: no launching into the shared default group or another lab's group.
  • KeepCrucibleTags, NoBlankDeleteTags: lab tags can't be changed or stripped.
  • OwnBuckets, OwnState: S3 buckets named crucible-lab-<id>… and only its own state file.
  • Read: Describe* calls, needed by Terraform (these are account-wide).

Why tags and not separate accounts per lab?One shared lab account is quick and cheap to run. Tags plus IAM conditions give each lab its own fence inside it. The trade-off is that isolation is best effort: a trainee can see (not change) other labs' resources through Describe calls. That is why a dedicated sandbox account is recommended.

Turn AWS labs on

Do this after Crucible itself is deployed. Labs stay off until all four steps are done.

  1. Create the labs stack in the lab account

    With credentials for the lab account. Add --crucible-account <id> when it is not Crucible's own account. Back up deploy/aws/labs/terraform.tfstate afterwards.

    crucible aws labs-init --region eu-west-1

  2. Turn on cost data

    In the payer (management) account: Billing → Cost allocation tags → activate crucible:lab-id, crucible:team and crucible:training. They appear after the first lab has run, and take up to 24 hours. Open Cost Explorer once in the lab account. It charges $0.01 per API call; Crucible makes 4–8 a day.

  3. Add an infracost key

    Free. Put it in crucible.tfvars as infracost_api_key. Without it, AWS labs can't be priced, so they can't be requested.

    infracost auth login

  4. Wire it in

    Run on the computer that holds the labs state. up reads the labs stack's outputs (role names, state bucket, allowed regions) and switches AWS labs on.

    crucible aws up

Then test it by hand.Nothing in the automated suites touches real AWS. docs/runbooks/aws.md lists every check: the lab identity, both tasks passing, a list of calls that must be refused, the sweep, the reaper, credential renewal after an hour, CloudTrail, tags on root volumes and the real bill. docs/test-guide.html has the same steps as a checklist.

Limits and good habits

Keep in mind

  • Trainees can read their own lab's Terraform state. Never put passwords, keys or tokens in lab state or outputs.
  • A credential leaked from a workspace stays valid up to an hour after the lab ends; leftovers it makes are reaped within about two hours.
  • An instance launched with a detached network interface (DeleteOnTermination=false) can leave an untagged interface behind. Check now and then: aws ec2 describe-network-interfaces --filters Name=status,Values=available.
  • The sweep and the reaper only look in allowed regions. End every lab in a region before removing it.

Good habits

  • Use a separate sandbox account for labs, with a budget alert of its own in AWS Budgets.
  • Run one Crucible per lab account: the reaper reports, but never deletes, labs it doesn't know.
  • Keep backups of the three local state files: persistent, labs, and your crucible.tfvars.
  • Try a new lab in dry-run mode on your machine first (make cluster-check), where a fake account stands in for AWS.
