Crucible Deploy Architecture

Crucible is one Go process that serves the API and the React app, backed by Postgres and an OIDC sign-in. The same process runs in three settings: on your laptop under Docker Compose, in the kind-based end-to-end check, and in production on a single k3s node in AWS, with AWS labs in a separate lab account. This page draws each one from the files in deploy/.

Local stack

Three containers and no Kubernetes. Open http://localhost:8080; you sign in on Keycloak, and the app talks to Postgres. Labs run outside Compose, through the laptop agent.

Start and stop it

crucible local up runs make build, make toolbox and ./scripts/seed-git.sh, then docker compose … up -d --build --wait. Add --keycloak-port 8082 when 8081 is taken. crucible local down stops it and keeps the data; --wipe deletes it.

Configuration

Settings, teams and budgets live in Postgres. CRUCIBLE_SEED_DIR imports examples/platform once, into an empty database only; its trainings' repositories arrive connected. CRUCIBLE_GIT_ALLOW_FILE=1 lets file:// repositories through, and a development CRUCIBLE_SECRET_KEY lets you try tokens and deploy keys under Administrator → Repositories.

Labs

The agent on your laptop runs laptop labs in Docker, and cluster labs on whatever cluster your kubeconfig points at. AWS labs are off here.

scripts/cluster-check.sh · deploy/compose/cluster.yml

cluster-check: the end-to-end proof

The same Compose stack, plus a kind cluster named crucible-m4 after milestone 4 (the cluster runtime). The API joins kind's Docker network and acts as the crucible service account, so the production RBAC and admission policy apply to it. It never touches ~/.kube/config or your platform cluster.

What it proves

Lab isolation on a real cluster: quota, the default-deny NetworkPolicy, the IMDS block, and that the service account can't write outside lab namespaces. Then the full browser journeys, including an AWS lab from estimate to Ledger and a cluster lab through the agent.

Why it takes ~35 minutes

Most of the time is building and booting: Go binaries, the web build and tests, the API and toolbox images, the kind cluster, the stack, then 12 journeys in sequence (about 8 minutes).

Faster loop

With KEEP=1 the stack stays up. Rebuild only the API and re-run one spec. Journeys that expect a fresh trainee need a fresh stack.

deploy/aws/persistent · deploy/aws/main · deploy/aws/labs

Production on AWS

Three Terraform stacks. persistent holds what must survive a rebuild: sign-in, the data bucket, Terraform state and the key that seals repository credentials. main is the node and everything around it; it can be torn down and rebuilt from the latest snapshot. labs lives in a separate, standalone AWS account, where trainees' AWS labs create real resources inside hard limits.

persistent

crucible aws init creates the Cognito user pool, the data bucket (release tarballs, nightly snapshots, the always-kept latest snapshot, trainees' uploads) and the Terraform state bucket, and keeps CRUCIBLE_SECRET_KEY as the SSM parameter /crucible/secret_key. Nothing here is ever destroyed, so a rebuilt node can still open the repository credentials in the restored database.

main

crucible aws up builds one EC2 node with an Elastic IP and installs k3s, Helm and sysbox on first boot. The scheduler stops it at night to save money; teardown then up rebuilds it and restores the newest snapshot.

Secrets

SSM holds the sign-in client secret, the database password, the quiz and webhook secrets and the optional git_credentials and smtp_password; each deploy copies them, and the smtp_* settings that are set, into the crucible-secrets Secret, with CRUCIBLE_SECRET_KEY (it seals connected repositories' tokens and deploy keys) from the persistent stack. A node set up before that key existed deploys without it and warns, until init is re-run. The SSH host keys Crucible pins live in Postgres, so a pod restart keeps them.

labs

crucible aws labs-init sets up the lab account: three roles, a permission boundary, the lab state bucket, a free billing export and an alert-only AWS Budget. The one manual step is activating the crucible:lab-id cost-allocation tag.

deploy/helm/crucible · rbac.yaml

Inside the node

k3s runs everything on the one node. The Helm chart installs Crucible, Postgres and the backup job in namespace crucible. Each AWS lab gets its own lab-<id> namespace, and estimates run in crucible-estimates. Two guards limit what the API's service account can do, even if the API itself were compromised.

Why one replica

The agent links, locks and live terminals are held in memory, so the chart pins replicas: 1 and a Recreate rollout. Scaling out would need a shared hub.

What IMDS is

The EC2 metadata service at 169.254.169.254, which hands out the node's credentials. Lab pods are cut off from it by the NetworkPolicy, a pod setting and an init guard that waits until the block is in place.

Backups

Every evening at 19:15 a CronJob dumps Postgres to snapshots/ (kept 30 days) and latest/ (kept for good). sleep, teardown and up take a snapshot first.

An AWS lab, start to finish

Each step names where it runs. Prices come from the free public AWS Price List, and spend from the lab's own Terraform state, then from the free billing export. If price data is missing or stale, the lab can't be requested; Crucible never quotes $0.

  1. Estimate crucible-estimates plan role

    A one-off pod runs terraform plan on the lab's module, with a read-only plan-role session (15 minutes) and no state. Crucible prices each planned resource from the price list it refreshes weekly, plus the author's declared prices and stated usage. The plan is cached per content version, and prices are applied fresh on every view.

  2. Request and approval crucible

    Estimate × the lab's hours picks an approval tier. Team budgets and caps are checked before anyone can approve. Over the lab's max_hourly_usd, it can't be requested at all.

  3. Apply lab-<id> lab role

    Crucible creates the lab namespace and a lab-role session tagged with the lab id (one hour, refreshed about every 45 minutes). A tf-apply pod builds the resources and writes labs/<id>.tfstate in the lab account. Crucible reads that state and starts metering.

  4. Work workspace pod

    The trainee uses the browser terminal with the lab's credentials, and Check runs server-side. Crucible re-reads the state every 15 minutes, so resources added from the terminal are metered too.

  5. End tf-destroy lab role

    The trainee ends the lab, or it expires, idles, hits its budget, or an admin stops all labs. A tf-destroy pod removes the resources, then a tag sweep catches anything Terraform didn't own. The meter stops when the destroy succeeds.

  6. Clean up ops role

    Every hour the reaper looks for resources still tagged with ended labs and deletes them. A lab's meter stays open until a full run finds nothing left.

  7. Billed billing export

    AWS writes the CUR 2.0 export daily. Crucible reads it every six hours, counted before credits. Billed spend replaces metered spend 48 hours after the lab ends. Independently, the AWS Budget emails admins at 80% and 100% of the month.
