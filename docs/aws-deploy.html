The result

What you'll end up with

One EC2 server in your AWS account runs single-node Kubernetes (k3s). On it run Crucible, its Postgres database and Traefik, which serves HTTPS with a Let's Encrypt certificate. People sign in through an Amazon Cognito user pool. Two Terraform stacks build it: persistent (sign-in, buckets, the secret key; never destroyed) and main (the server and everything around it). A second AWS account for AWS labs is optional (in our account there is only one; see In our account).

What it costs

The design's estimate for eu-west-1, on demand: the t3a.xlarge node about $40 a month when it sleeps outside working hours (11 h × 22 days), about $119 if it runs 24/7. Add the 60 GiB disk (about $5.30), the Elastic IP (about $3.70) and S3 (under $1). That makes about $50 a month on the schedule, about $130 around the clock, plus what labs spend. Asleep, it costs about $10 a month. Check current AWS prices; Every component has the table.

In our account: no Elastic IP, so take about $3.70 a month off. The region is il-central-1, so prices differ from these.

The cost drivers

The instance type and how many hours it runs. t3a instances also bill surplus CPU credits if they stay busy above their baseline (40% for t3a.xlarge), about $0.05 per vCPU-hour; watch the CPUSurplusCreditsCharged metric. Cognito, the scheduler, SSM and the lab account's billing export and Budget are free at this size.

Cluster labs are opt-in

Cluster labs run on trainees' own clusters and need a toolbox image. Build it for arm64 and amd64, push it, and set toolbox_image in crucible.tfvars to its digest (<registry>/crucible-toolbox@sha256:<64 hex>; a tag is refused). Left empty, cluster labs stay off. Laptop labs and AWS labs work either way. The runbook's toolbox section has the build commands.

Our deployment

In our account: what's different

The rest of this page describes a standard install: an Elastic IP, a domain, HTTPS, and a separate lab account. Ours is not that. We have one AWS account (il-central-1, inside an AWS Organizations landing zone), its VPC has no inbound path, and for now we reach the app over SSM. Where a step differs, a note headed "In our account" says how.

  1. One account, for Crucible and for labs

    Run crucible aws labs-init with our own credentials and without --crucible-account. The labs stack then trusts the node role in this same account. It also turns on S3's account-wide public-access block for it.

  2. No Elastic IP, no DNS record, no Let's Encrypt

    The organization's policies deny Elastic IPs, internet gateways, load balancers, VPC endpoints, subnets and routes. A public IP on an instance is allowed but unreachable, and Let's Encrypt's check can't reach the node. So there is no public URL, and the "point DNS" and "wait for HTTPS" steps do not apply.

  3. Access is a Session Manager port-forward

    Each person with our Identity Center access forwards a local port to port 80 on the node and opens http://localhost:18080. Everyone must use the same local port, because Crucible's public URL has to match the browser's address. Setup and the connect script: Reaching the app over SSM; the design: access over SSM.

  4. Later: a Cloudflare Tunnel

    A future option is an outbound-only Cloudflare Tunnel from the node, gated by Cloudflare Access. It needs security-team approval and is not built. See the Cloudflare option.

Before this works here.The stack as built cannot deploy in our account yet. These changes to deploy/aws/main and internal/awsops are not made:

  • take an existing VPC and subnet as variables (the workload subnet spokeSubnet1) instead of looking up the default VPC;
  • create no Elastic IP and no Route 53 record, and open no inbound security-group rules;
  • serve plain HTTP from Traefik: no Let's Encrypt, no redirect to HTTPS;
  • set the public URL and the Cognito callback to http://localhost:18080;
  • have up and status check health over SSM instead of the public URL.

Until they land, the commands below are the standard ones and will fail here at the points the notes mark.

AWS permissions

Use administrator rights in the account. The stacks create S3 buckets, a Cognito user pool, SSM parameters, IAM roles and policies, an EC2 instance, a security group, an Elastic IP, EventBridge Scheduler schedules and, optionally, a Route 53 record. Day to day you also run SSM commands and start and stop the instance. The runbook gives no minimal policy.

In our account: we sign in through Identity Center as Workload-Admin-PS. Organization policies (SCPs) deny ec2:AllocateAddress, ec2:CreateInternetGateway, elasticloadbalancing:CreateLoadBalancer, ec2:CreateVpcEndpoint, ec2:CreateSubnet, ec2:CreateRoute and ec2:CreateClientVpnEndpoint. EC2 instances in the spoke subnets, security groups and IAM roles are allowed. S3, Cognito, SSM parameters, EventBridge Scheduler, Budgets, Data Exports and ssm:StartSession are not yet checked.

These are your own role's permissions. The node and the lab roles are made by the stacks; see IAM roles.

A domain you control

Pick the final hostname now, such as crucible.example.com. The Cognito sign-in callback is built from it, and Let's Encrypt issues the certificate for it. You'll either add an A record by hand at your DNS provider, or give Terraform a Route 53 hosted zone that holds the name.

In our account: no domain is needed for SSM access. init still requires --domain today; see init.

The region

init takes the region, and everything in the main account follows it: the node goes where the user pool is. The account needs its default VPC in that region, because the node is placed in its first default subnet; up fails without one. Labs' regions are set separately, in the lab account.

In our account: the organization deletes the default VPC, so this check returns [] and create-default-vpc is not an option. The stack must take our VPC (vpc-03aa39198d92c5a25) and spokeSubnet1 as variables; not built yet.

aws ec2 describe-vpcs --region eu-west-1 --filters Name=is-default,Values=true --query 'Vpcs[].VpcId'   # [] means none
aws ec2 create-default-vpc --region eu-west-1      # only if there is none

AWS labs or not

AWS labs create real resources, so they belong in a second, standalone AWS account (we have only one; see below). The runbook strongly recommends one: the permission boundary limits labs to EC2 and S3, small instances and allowed regions, but isolation in a shared account is best-effort. You can add labs later; Crucible works without them.

In our account: there is no second account, so labs share this one and isolation is best-effort. See AWS labs.

deploy/aws/persistent · once per account

One-time setup: crucible aws init

This creates everything that must outlive the server. Nothing here is ever destroyed by Crucible.

In our account.--domain is required today and feeds the Cognito callback (https://<domain>/auth/callback). For us the callback must be http://localhost:18080/auth/callback (Cognito accepts plain http only for localhost). init cannot take that yet, so what to pass for --domain in the meantime is open.

  1. Run init main account

    crucible aws init --region eu-west-1 --domain crucible.example.com

    Runs with your own role. Both flags are required. It runs terraform init, then terraform apply in deploy/aws/persistent. Terraform shows the plan and asks Enter a value:. Read it, then type yes. In a fresh account the plan adds 14 resources:

    • the state bucket crucible-<account>-tfstate (versioned, private): it holds the main stack's state;
    • the data bucket crucible-<account>-data (versioned, encrypted, private): releases, nightly snapshots (kept 30 days), latest/ (kept for good) and trainees' uploads;
    • the Cognito user pool crucible, its login domain crucible-<account>.auth.<region>.amazoncognito.com, the app client crucible (callback https://<domain>/auth/callback) and its login style. Invite-only, email as username, deletion protection on;
    • the SecureString /crucible/secret_key, which is CRUCIBLE_SECRET_KEY: it seals the repository tokens and deploy keys Crucible stores. Terraform never changes or deletes it once made.

    Every resource has prevent_destroy or deletion protection. To see each one's settings, read docs/runbooks/cognito.md and the every component.

  2. Check it worked

    terraform -chdir=deploy/aws/persistent output
curl -s "$(terraform -chdir=deploy/aws/persistent output -raw oidc_issuer)/.well-known/openid-configuration" | jq .issuer
aws ssm get-parameter --region eu-west-1 --name /crucible/secret_key --query Parameter.Name --output text

    The outputs list cognito_login_url, cognito_user_pool_id, data_bucket, oidc_client_id, oidc_issuer, region and state_bucket. The curl prints the same issuer back. The last command prints /crucible/secret_key without showing the value.

  3. Back up the persistent state, now

    deploy/aws/persistent/terraform.tfstate is local and git-ignored. It's the only record of what init created. Lose it and you have to import 14 resources by hand (see lost persistent state). It also holds the secret key and the Cognito client secret in plain text, so keep the copy private. Copy it to the state bucket or to a password manager, and do it again after every init.

    aws s3 cp deploy/aws/persistent/terraform.tfstate \
  "s3://$(terraform -chdir=deploy/aws/persistent output -raw state_bucket)/persistent.tfstate"

    A copy in the same account doesn't help if you lose the account. Keep a second copy elsewhere if that matters to you.

Never lose or rotate the secret key.Every token and deploy key sealed with it becomes unreadable, and each of those repositories has to be connected again. It survives teardown because it lives in the persistent stack.

deploy/aws/main · internal/awsops

Build the node: crucible aws up

One command builds the server, waits for it, and ships the release you have checked out. --var-file defaults to deploy/aws/main/crucible.tfvars.

In our account.as built, up fails at the apply: it looks up a default VPC that does not exist here, and tries to allocate an Elastic IP, which an SCP denies. The "Tells you where to point DNS" and "Waits for HTTPS" steps do not apply; once the changes above are made, up checks health over SSM instead.

crucible aws up

  1. Reads the persistent stack your computer

    It needs deploy/aws/persistent/terraform.tfstate. Without it, it stops with the persistent stack has no state_bucket output: run `crucible aws init` first.

  2. Initialises the main stack's backend

    terraform init -reconfigure, with state in the state bucket under main.tfstate and S3 locking.

  3. Snapshots a running node first

    Only when a node already exists. A running node is backed up before the apply, in case it gets replaced. A stopped node relies on its last snapshot. Any other state stops up. On the first run there's nothing to back up.

  4. Wires AWS labs, if their stack is here

    If it can read deploy/aws/labs's outputs, it turns AWS labs on. If it can't, and labs are off, it leaves them off without an error. If labs are already on and it can't read the outputs, it stops (see AWS labs).

  5. Applies main account

    Runs with your own role, which creates the node role below. Terraform shows the plan and asks for yes. It creates:

    • a security group crucible-web: 80 and 443 in from anywhere, no SSH (the shell goes through SSM);
    • the node role and instance profile crucible-node: the identity the node uses for S3, SSM and, with labs on, the lab roles (what it may do: IAM roles);
    • SSM parameters: /crucible/env and /crucible/helm-values (settings), and five SecureStrings (see Secrets);
    • the EC2 node crucible: the current Ubuntu 24.04 amd64 image, IMDSv2 only, an encrypted gp3 disk;
    • an Elastic IP, and the Route 53 A record if you gave a zone;
    • with the schedule on, the role crucible-scheduler and the schedules crucible-wake and crucible-sleep.

  6. Tells you where to point DNS

    Right after the apply it prints:

    Point an A record crucible.example.com → 203.0.113.10 now (skip if route53_zone_id is set).

    Create that record at your DNS provider while up carries on: the build and the node's first boot give you a few minutes. With route53_zone_id set, Terraform already did it. Check it with dig +short crucible.example.com.

  7. Ships the release your computer node

    It runs the same steps as crucible aws deploy: build, upload, then run the node's deploy script through SSM. That waits for the node's first boot to finish.

  8. Waits for HTTPS

    It polls https://<domain>/healthz until it answers 200. Success ends with the forge is lit: https://crucible.example.com and <sha> is live at https://crucible.example.com.

What the node does on first boot

Cloud-init runs deploy/aws/main/bootstrap.sh.tftpl. Everything it prints goes to /var/log/crucible-bootstrap.log.

In our account.the "Configures Traefik" step must change: Traefik has to serve plain HTTP on port 80, with no Let's Encrypt request and no redirect. Today it redirects to HTTPS, which breaks the tunnel. Outbound calls (S3, SSM, STS, package downloads) leave through the central firewall and NAT; which hosts it allows is not verified.

  1. Prepares the machine

    Sets the time zone to schedule_timezone, installs unzip and curl, then AWS CLI v2.

  2. Configures Traefik

    Writes a k3s manifest so Traefik, which comes with k3s, gets a Let's Encrypt certificate by HTTP-01 on port 80 and redirects HTTP to HTTPS.

  3. Installs sysbox

    Downloads the pinned Sysbox CE package, checks its sha256, installs it, registers the sysbox-runc runtime with k3s's containerd and adds the sysbox-runc RuntimeClass. If this fails it prints WARNING: sysbox install failed; AWS labs stay unavailable and carries on: Crucible still comes up.

  4. Installs k3s and Helm

    k3s at k3s_version, then Helm 3.18.4.

  5. Reads its settings and writes its scripts

    Fetches /crucible/env from SSM, then writes /opt/crucible/deploy.sh (imports a release and installs the chart) and /opt/crucible/snapshot.sh (runs the backup now).

  6. Tries a first deploy

    Runs deploy.sh once. On a brand-new install no release is published yet, so it prints no release published yet, and that's expected. On a rebuilt node it deploys the last release, and the chart's restore step loads the newest snapshot into the empty database.

  7. Marks itself ready

    Touches /opt/crucible/.ready. If any step before this failed, it touches /opt/crucible/.failed instead, and deploy reports node bootstrap failed.

The runbook gives no typical duration. Most of the time goes on the local image build and the node's first boot. These are the limits in internal/awsops:

internal/awsops Deploy · deploy.sh

Ship the app: crucible aws deploy

Ships the commit you have checked out. up already ran it once. Run it yourself for every later release. The node must be running: if it's asleep, it stops at once with node is stopped; run `crucible aws wake`.

crucible aws deploy

  1. Names the release your computer

    The release is the 12-character commit id. With uncommitted changes it becomes <sha>-dirty-<unix time>, so commit first if you want a clean name.

  2. Builds

    docker buildx build --platform linux/amd64 -t crucible:<sha> --load ., then docker save and gzip it, then helm package deploy/helm/crucible. Everything goes to .local/release/.

  3. Uploads data bucket

    releases/<sha>/crucible-image.tar.gz, releases/<sha>/chart.tgz, then current-release, which names the sha. It prints release <sha> published; rolling out…. There's no container registry.

  4. Rolls out node, via SSM

    Your role sends the command; the node runs it with the node role. aws ssm send-command waits for .ready, then runs /opt/crucible/deploy.sh. That re-reads /crucible/env, downloads the release, imports the image into k3s, rebuilds the crucible-secrets Secret from SSM, and runs helm upgrade --install with /crucible/helm-values.

  5. Checks health

    Polls /healthz as up does, and prints <sha> is live at <url>.

Watch the output for one warning. WARNING: no /crucible/secret_key: tokens and deploy keys stay refused until you re-run 'crucible aws init', then 'crucible aws deploy' means this install predates the secret key. See Upgrading.

Check the deploy

crucible aws status
curl -fsS -o /dev/null -w '%{http_code}\n' https://crucible.example.com/healthz      # 200
aws s3 cp "s3://$(terraform -chdir=deploy/aws/persistent output -raw data_bucket)/current-release" -   # the sha you shipped

Then look inside the node. Open a shell over SSM (no SSH port is open; how a Session Manager shell works):

aws ssm start-session --region eu-west-1 --target "$(terraform -chdir=deploy/aws/main output -raw instance_id)"
sudo k3s kubectl -n crucible get pods                         # crucible and postgres Running

sudo k3s kubectl -n crucible logs deploy/crucible -c api      # the app
sudo k3s kubectl -n crucible logs deploy/crucible -c restore  # "database already initialised", "restored …" or "fresh install"
systemctl is-active sysbox                                    # active
sudo k3s kubectl get runtimeclass sysbox-runc

The image line ends in crucible:<sha>. Then open https://crucible.example.com in a browser: you should land on the Cognito sign-in page.

docs/runbooks/cognito.md · in-app Docs

First sign-in and setup inside Crucible

Configuration lives in Crucible's database, not in git or Terraform. You set it up in the app as the first admin. The in-app Docs (https://<domain>/docs) cover each page in full.

In our account.open the SSM tunnel first, then use http://localhost:18080 wherever this section says https://<domain>. GitHub webhooks cannot reach us, so skip the webhook step: Crucible fetches every 60 seconds anyway. Laptop agents reach Crucible only while a tunnel is open.

  1. Invite the bootstrap admin in Cognito

    You can do this any time after init. Use the same email as bootstrap_admin. Add --region if your AWS CLI's default region is a different one.

    POOL=$(terraform -chdir=deploy/aws/persistent output -raw cognito_user_pool_id)

aws cognito-idp admin-create-user \
  --user-pool-id "$POOL" \
  --username you@example.com \
  --user-attributes Name=email,Value=you@example.com Name=email_verified,Value=true Name=name,Value="Your Name" \
  --desired-delivery-mediums EMAIL

    You get "You've been invited to Crucible" with a temporary password, valid for 7 days. Cognito's own sender allows about 50 emails a day. Everyone else is invited the same way. cognito.md covers resending, resets, removal and MFA.

  2. Sign in

    Open https://<domain>, sign in with the email and the temporary password, and choose your own (12 characters or more, with upper case, lower case and a number). You come back to Crucible as an admin: Administrator shows in the top bar.

  3. Forge settings

    Administrator → Forge settings. Set the three cost tiers (all three or none). Without them, labs that cost money can't be requested: Crucible fails closed. Add a second admin: the page asks while there's only one. Add any lab schedules trainings will use. Every save is audited.

  4. Teams

    Teams → + Start a team: an id, a name and the first leader's email, then Create team. Add people under Add someone. Each person needs a Cognito account too, with the same email.

  5. Repositories

    Administrator → Repositories. Connect each git repository once, then Test connection.

    • HTTPS with an access token: for a private repository, or any whose content people will edit in Crucible. GitHub: a fine-grained token for that one repository with Contents: Read and write. GitLab: a project access token with write_repository.
    • SSH with a deploy key Crucible makes: for ssh:// or git@host:path. Crucible shows the public key. Add it at your host with write access. Crucible pins the host's key on first contact and keeps it in Postgres.
    • No credential of its own: a public repository, or an https:// one that git_credentials reaches.

    The result reads Reachable with Can write or Read only. The test asks the host to start a push and stops before sending anything. Read only means edits made in Crucible can't be submitted. If the page says it can't keep a credential, the secret key is missing: see Upgrading.

  6. Register trainings

    Administrator → Trainings (or Manage trainings) → + New training. Pick the connected repository, the branch, tag or commit to follow (usually main), the folder holding training.yaml, and, as an admin, the owning team. Then enroll people and give out roles on the same page.

  7. The git webhook (optional)

    Crucible fetches content every minute anyway (syncInterval: 60s). A push webhook makes it fetch at once. Point it at POST https://<domain>/api/git/hook with the hook secret:

    aws ssm get-parameter --with-decryption --name /crucible/git_hook_secret --query Parameter.Value --output text
    • GitHub: content type application/json, the secret in the webhook's Secret field. GitHub signs each delivery (X-Hub-Signature-256) and Crucible checks the signature. Bodies over 1 MiB are refused.
    • GitLab: the secret in the webhook's Secret token field (sent as X-Gitlab-Token).
    • Any other host: a custom header X-Crucible-Secret set to the secret.

    A right secret gets 202. Anything else gets 404. The secret changes on every teardown → up: update the webhook then.

  8. Email (optional)

    Without SMTP, Crucible sends no email; Slack and Teams webhooks still work. To turn it on, set the SMTP settings in crucible.tfvars and run crucible aws up:

    smtp_addr     = "email-smtp.eu-west-1.amazonaws.com:587"   # host:port
smtp_from     = "Crucible <crucible@example.com>"
smtp_username = "AKIA…"
smtp_password = "…"                                         # a SecureString, /crucible/smtp_password

    Every deploy copies the ones you set into crucible-secrets as CRUCIBLE_SMTP_*, so they survive teardown → up. A deploy of the release already running doesn't restart the API, so after a change run this on the node:

    sudo k3s kubectl -n crucible rollout restart deploy/crucible

    An empty setting is never written, so keys you added by hand with kubectl edit secret crucible-secrets stay. A node built before these settings existed keeps its old deploy script, which ignores them: keep the hand-added keys, or rebuild the node.

deploy/aws/labs · optional

Optional: AWS labs

Do this after Crucible itself works. AWS labs run Terraform in the lab account with one-hour credentials scoped to one lab. Crucible prices them itself from the public AWS Price List, meters them from each lab's Terraform state, then replaces that with the free billing export. How it works, and what the permission boundary allows: an AWS lab, start to finish and the IAM fence.

In our account.the lab account is our account. Run labs-init with our own credentials and without --crucible-account. Lab instances and security groups go in the spoke subnets, get no public IPs, and leave through the same firewall. Lab modules that create Elastic IPs, NAT gateways or load balancers fail, denied by the SCPs as well as by the lab role. The permission boundary is the only isolation between labs and Crucible itself.

  1. Run labs-init lab account credentials

    Runs with your own role in the lab account; it creates the lab, ops and plan roles (IAM roles).

    crucible aws labs-init --region eu-west-1 \
  --crucible-account 111122223333 \
  --budget-usd 200 --budget-email ops@example.com
    • --region (required): the lab state bucket's region, and the only lab region unless you pass --allowed-regions.
    • --allowed-regions eu-west-1,eu-central-1: the regions labs may use, comma-separated (the stack's allowed_regions). It must include --region; labs-init refuses it otherwise, before running Terraform. A re-run without it keeps the current list. up passes the list to the node, so run up after changing it.
    • --crucible-account: the account id that runs Crucible, when it isn't this one. It becomes the stack's crucible_account_id. The lab roles then trust that account's node role.
    • --budget-usd and --budget-email (repeat, at most 10): the alert-only AWS Budget crucible-labs-monthly, which emails at 80% and 100% of the month's actual spend. With no email, no budget is made. Without --budget-usd the first run uses $100. A negative amount is refused. A re-run keeps each value you leave out.

    It creates the lab, ops and plan roles under a permission boundary, the lab state bucket crucible-<account>-labstate, the export bucket crucible-<account>-labexports and the CUR 2.0 export crucible-labs (Data Exports live in us-east-1). It also turns on account-wide S3 Block Public Access. The lab roles trust the node role by exact name. labs-init reads it from main's node_role_name output when it can. With lab-account credentials it usually can't, so it prints a note and trusts crucible-node, which is right unless you changed name.

  2. Back up the labs state

    deploy/aws/labs/terraform.tfstate is local too. Back it up as you did the persistent state. Every later up must run where this file is.

  3. Activate the cost-allocation tag Billing console

    The one step by hand, and free. Billing → Cost allocation tags, then activate crucible:lab-id. Do it in the management (payer) account if the lab account is in an organization, otherwise in the lab account. The tag shows up there only after a tagged resource has existed, which can take up to 24 hours, so come back after your first lab. Activation isn't retroactive unless you ask for a backfill. Until it's active, billed spend stays empty and the Ledger shows metered spend.

  4. Wire it in Crucible account credentials

    Your own role again; from then on the node role assumes the lab roles.

    crucible aws up

    Run it on the machine that holds the labs state. up reads its outputs (the roles, state bucket, regions, plan role and export) and turns AWS labs on. Check the node afterwards: systemctl is-active sysbox must print active.

  5. Check the first billing export, a day later

    The first export arrives within about 24 hours. With lab-account admin credentials:

    aws bcm-data-exports list-exports --region us-east-1                # lists crucible-labs
aws s3 ls s3://crucible-<lab account>-labexports/cur/ --recursive   # Manifest.json and .csv.gz files under crucible-labs/

    Then terraform -chdir=deploy/aws/labs plan with the same -vars labs-init passed must show no changes.

Prices

Crucible downloads the public AWS Price List for the allowed regions every week, and at start when its prices are more than 6 days old. The node needs outbound HTTPS to pricing.us-east-1.amazonaws.com. Admins see Price data from <date> on the Ledger. If prices are missing or older than 30 days, that line turns red ("Out of date: AWS labs can't be estimated or requested until it refreshes"), with the last error. Estimates fail closed; Crucible never quotes $0.

Check an estimate works

Open an AWS lab's page as one of its training's editors or admins. It shows a non-zero estimate, and How this estimate was worked out lists each priced resource. A failure shows "The estimate failed …" to editors, and only "the lab can't be requested right now" to participants. On the node: sudo k3s kubectl -n crucible-estimates get pods (tf-plan-*) and sudo k3s kubectl -n crucible logs deploy/crucible -c api | grep 'lab quote failed'.

Prove it on a sandbox

Nothing automated touches real AWS. The runbook's "Verify on a real sandbox" lists every check by hand: the lab identity, calls that must be refused, the sweep, the reaper, credential refresh, CloudTrail, tags and costs. docs/test-guide.html has them as a checklist.

Once labs are on, keep running up where the labs state is.If up can't read the labs outputs, it stops rather than turning labs off, because running labs would lose credential refresh, destroy and the sweep. --no-labs turns them off on purpose: end every AWS lab first. teardown never touches the labs stack.

Existing installs

Upgrading an existing install

For example, after pulling a version that adds the secret key and free FinOps. The runbook gives each piece separately. This is the order its rules imply: init before deploy, and labs-init before up.

  1. Check out the new version

    Pull and check out the commit you want to ship, with a clean working tree. Make sure deploy/aws/persistent/terraform.tfstate is here (copy it back from your backup on another machine).

  2. Re-run init with the same region and domain main account

    crucible aws init --region eu-west-1 --domain crucible.example.com

    It re-applies the persistent stack where its state lives and adds only the secret key: the plan should add random_password.secret_key and aws_ssm_parameter.secret_key, and change nothing else. If it wants more, stop and compare. If your crucible.tfvars sets another name, copy the new parameter to /<name>/secret_key. Then back up the persistent state again.

  3. If you use AWS labs: re-run labs-init lab account

    crucible aws labs-init --region eu-west-1 --crucible-account 111122223333 \
  --budget-usd 200 --budget-email ops@example.com

    Do this before up: main now refuses AWS labs without the plan role and the export, and says so. Pass both budget flags on this first re-run, because an older stack has no budget outputs to read back. Leave out --crucible-account if you never used it. Remove infracost_api_key from crucible.tfvars; it's no longer a variable. Back up the labs state. Then activate the cost-allocation tag (see AWS labs).

  4. Ship it main account

    crucible aws up        # if you re-ran labs-init or changed crucible.tfvars; it ends by deploying
crucible aws deploy    # otherwise

    Run up where the labs state is. The deploy output must not show WARNING: no /crucible/secret_key.

  5. Restart the API, if the release was already running

    A deploy of the release already running doesn't restart the API, so it won't see the new key. On the node:

    sudo k3s kubectl -n crucible rollout restart deploy/crucible

    A new commit rolls the pod anyway. The restart is then harmless, apart from a few seconds offline.

  6. Check

    crucible aws status shows healthz: ok. Administrator → Repositories no longer says it can't keep a credential.

Old nodes need a rebuild.Terraform never applies first-boot script changes to a running node. A node built before sysbox (M4) has none, and one built before M6 has an older deploy.sh. Rebuild either with crucible aws teardown --yes, then crucible aws up. The data comes back from the latest snapshot.

Disaster recovery

Teardown, restore and disaster recovery

  1. Tear down

    crucible aws teardown --yes

    Takes a snapshot, then terraform destroy on the main stack without asking again. The buckets, snapshots, uploads, Cognito users, the secret key and the labs stack all survive. Without --yes it refuses. It reads crucible.tfvars (or --var-file) like up.

  2. Rebuild

    crucible aws up

    A new node boots, and the chart's restore step loads the newest snapshot into the empty database before Crucible starts. If the dated snapshots have expired, it falls back to latest/crucible-latest.dump. Content comes back from git.

  3. Re-point DNS

    The Elastic IP changes after a teardown. Update the A record to the IP up prints. With route53_zone_id it's automatic.

  4. Update the webhook

    The git webhook secret is regenerated. Read it again and update each repository's webhook.

What survives

The secret key, so restored repository tokens and deploy keys still open. Pinned SSH host keys, because they're in the database. Cognito users. Uploads. The labs stack.

What changes

The Elastic IP, the webhook secret, the database password and the quiz secret. They're all in the main stack. A new quiz secret reshuffles quizzes in progress. SMTP keys you added by hand are gone; the smtp_* settings come back. Anything written after the teardown's snapshot is lost, so the snapshot must succeed (it refuses to go on otherwise).

Second machine or fresh clone

Copy the persistent state back first (and the labs state, if you use labs), then run crucible aws up. It's idempotent, and it sets up the S3 backend that deploy and the others need.

Lost persistent state

First, restore your backup:

aws s3 cp s3://crucible-<account>-tfstate/persistent.tfstate deploy/aws/persistent/terraform.tfstate

With no backup at all, run terraform -chdir=deploy/aws/persistent init, then terraform import each of the 14 resources, using the real ids from the console: aws_s3_bucket.state, aws_s3_bucket_versioning.state, aws_s3_bucket_public_access_block.state, aws_s3_bucket.data, aws_s3_bucket_versioning.data, aws_s3_bucket_server_side_encryption_configuration.data, aws_s3_bucket_public_access_block.data, aws_s3_bucket_lifecycle_configuration.data, aws_cognito_user_pool.users, aws_cognito_user_pool_domain.login, aws_cognito_user_pool_client.crucible, aws_cognito_managed_login_branding.crucible, aws_ssm_parameter.secret_key (id /crucible/secret_key) and random_password.secret_key (id: the parameter's current value, read with aws ssm get-parameter --with-decryption).

Import the secret key before any plan, and never apply against an empty state.Without the import, Terraform makes a new key and every stored repository credential stops opening. An apply against empty state tries to create duplicates. After the imports, run terraform plan with -var region=… and -var domain=… and import anything it still wants to create.

When it doesn't work

Troubleshooting

Every command below runs on the node, in an SSM session, unless it starts with crucible.

In our account.the certificate and DNS entry below do not apply. If the app does not answer, check in order: the node is running (the after-hours automation may have stopped it), the SSM tunnel is open on 18080, then Traefik is serving HTTP on port 80. Sign-in errors here usually mean the Cognito callback is not http://localhost:18080/auth/callback, or the browser uses another port.

No certificate, or HTTPS never answers

Symptom

status stays at healthz: not answering; the browser shows a certificate warning or nothing.

Cause

DNS doesn't point at the Elastic IP yet, or port 80 isn't reachable, so Let's Encrypt's HTTP-01 challenge fails.

Fix

Check dig +short <domain> against the IP up printed, and that port 80 is open. Then read Traefik's log:

sudo k3s kubectl -n kube-system logs deploy/traefik

If the Traefik chart that came with your k3s rejects ports.web.redirections, use ports.web.redirectTo: {port: websecure} in /var/lib/rancher/k3s/server/manifests/traefik-config.yaml.

Bootstrap failed

Symptom

deploy or up stops with node bootstrap failed - see /var/log/crucible-bootstrap.log.

Cause

A first-boot step failed, and /opt/crucible/.failed exists.

Fix
sudo tail -f /var/log/crucible-bootstrap.log
# after fixing the cause:
sudo rm /opt/crucible/.failed

Then run crucible aws deploy again.

Sysbox failing

Symptom

AWS labs fail to start. The boot log shows WARNING: sysbox install failed, or a lab pod reports no runtime for "sysbox-runc".

Cause

The sysbox install failed (the rest of the node came up without it), or containerd didn't load the sysbox template.

Fix
systemctl is-active sysbox
sudo journalctl -u sysbox -u sysbox-mgr --no-pager | tail -50
sudo grep -A3 sysbox-runc /var/lib/rancher/k3s/agent/etc/containerd/config.toml
sudo systemctl restart k3s      # if the sysbox-runc block is missing

Also look at /var/log/cloud-init-output.log. A node built before sysbox existed needs a rebuild.

An AWS lab stuck in "provisioning"

Symptom

The lab sits in provisioning, then fails with terraform apply failed: … or "could not be started".

Cause

The lab's Terraform failed, often a permission the boundary refuses, or the workspace pod can't start.

Fix
sudo k3s kubectl -n lab-<id> get pod tf-apply -o jsonpath='{.status.containerStatuses[0].state.terminated.message}'
sudo k3s kubectl -n lab-<id> describe pod lab

The trainee sees the same log tail. A runtime error on the lab pod points back to sysbox. An UnauthorizedOperation can be decoded with aws sts decode-authorization-message (admin credentials); the runbook explains the common cases.

Estimates unavailable

Symptom

A lab can't be requested: "AWS price data is out of date; an admin needs to refresh it", "Crucible can't price: <types>", or editors see "The estimate failed …".

Cause

Price data missing or over 30 days old (usually no outbound HTTPS to pricing.us-east-1.amazonaws.com), or the plan failed. The plan role can only ec2:Describe*, s3:GetBucket* and s3:ListAllMyBuckets, so a data source needing more fails. Or a resource Crucible can't price (io2, an unknown size, an instance type not offered in that region).

Fix

Look at the Ledger's price line and its last error, and use Refresh now. The job queue retries failed refreshes with backoff. For plan errors:

sudo k3s kubectl -n crucible logs deploy/crucible -c api | grep 'lab quote failed'
sudo k3s kubectl -n crucible-estimates get pods

A failed plan is retried after 5 minutes. The lab's authors fix the module or declare prices under aws.prices.

Missing secret key warning

Symptom

deploy prints WARNING: no /crucible/secret_key …. Repositories says it can't keep a credential, and refuses tokens and deploy keys.

Cause

The install predates the key, or crucible.tfvars sets a name other than crucible.

Fix

Follow Upgrading: init with the same region and domain, deploy, the rollout restart, then a new state backup. With another name, copy the parameter to /<name>/secret_key.

Snapshot refusals

Symptom

up, sleep or teardown stops with snapshot failed, not applying (or not stopping, not tearing down), node is <state>; wait until the node is stable, or cannot determine node state.

Cause

These commands back up first and refuse to go on if the backup fails, or while the node is starting or stopping.

Fix

Wait until the node is running or stopped, and retry. Read the backup job's log with sudo k3s kubectl -n crucible get jobs. If the node is broken and can't snapshot, add --no-snapshot: everything since the last backup is lost if the disk goes.

The node is asleep

Symptom

deploy, snapshot or the end of up says node is stopped; run `crucible aws wake`.

Cause

The schedule stopped it, or you ran sleep.

Fix

crucible aws wake, then run the command again.

up won't read the labs stack

Symptom

aws labs are on (…) but the labs stack outputs cannot be read.

Cause

You ran up on a machine without deploy/aws/labs/terraform.tfstate.

Fix

Run it where that file is, or restore it from your backup. Use --no-labs only to turn AWS labs off on purpose.

Sign-in errors

Symptom

Cognito says redirect_mismatch, or Crucible shows "invalid id token" or rejects an unverified email.

Cause

The domain differs from init's --domain; the issuer is from another region; the user's email_verified is false.

Fix

Re-run crucible aws init with the exact hostname, or re-run up. For the email, see cognito.md §9.

App logs: sudo k3s kubectl -n crucible logs deploy/crucible -c api and -c restore.
